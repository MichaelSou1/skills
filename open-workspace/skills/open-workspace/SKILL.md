# 开辟新工作区

将用户选定的研究或开发方向落为可接手的工作区。本技能**只能由用户手动触发**，不能因发现论文、形成新 idea 或判断需要独立目录而自行调用。Codex 的 `agents/openai.yaml` 禁止隐式调用；兼容支持该字段的客户端使用 `disable-model-invocation: true`。

触发后按用户提供的项目名、源仓库、服务器和约束推进，完成本机目录、开发约定、私有仓库及可选远端同步。用户已授权这些步骤时不反复询问确认；此授权不包括模型/数据下载、安装训练环境、启动实验、消费 API 额度或创建新的 Codex 聊天。

## 1. 确认输入与已有状态

- 从对话获取项目名或可确定的短名、研究目标、是否有源仓库、是否指定服务器。新项目默认使用安全 slug（字母/数字开头，其后仅字母、数字、点、下划线或连字符，不含路径分隔符）；已有或用户指定的路径保留原意，动态 shell 参数严格引用，不能把未经处理的名称拼入命令。项目名确实无法确定时询问最小必要信息；其他独立核查可以继续。
- **未指定服务器，就仅完成本机与 GitHub。** 不沿用旧项目的 SSH alias、record、节点、目录或凭据。指定服务器后读取 [远端部署流程](references/remote-bootstrap.md)。
- 记录检查时间与时区；当用户说“当前/最新”时现场或联网核实。以实际本机 `gh` 登录账号和用户指定 owner 为准，不硬编码账号。
- 先检查拟用目录、适用 AGENTS、Git working tree、branch、remotes，以及目标 GitHub 仓库是否存在。不得把同名目录当空目录，检查真实路径、符号链接、嵌套 Git 和未提交文件；已有 Git 的 `--show-toplevel` 必须对应拟管理工作区，不误操作其父仓库。

## 2. 建立本机工作区与开发约定

1. 未建立工作区时，在本机实际家目录创建 `<project>` 文件夹；用户给定已有目录则复用。路径出现争用或已有无关内容时保留原内容，选择明确的新目录或询问，不覆盖。首次 clone 用户选定的源码时保留上游历史和许可证。
2. 读取 [AGENTS 模板](assets/AGENTS.template.md)，提炼并适配为工作区根目录 `AGENTS.md`。写明它约束开发协作者，不是被训练模型的 system prompt；**必须明确规定使用 conda 管理本项目环境依赖**，采用项目运行时根下的隔离 prefix，不以 venv、uv 或系统 Python 替代。这里只写入环境约定，不自动安装或创建 conda 环境。
3. 填入已知目标、本机绝对路径、GitHub URL 与执行规则；没有计划、环境入口、实验或测试证据的字段写“尚未建立/待核实”，不虚构文件。模板占位符必须替换；无远端时运行时目录通常为家目录下 `<project>-data`，删除服务器、worker、deploy key 与远端执行约定。远端确认为 KML 时保留模板的 KML 占卡程序段落，填写 `kml_idle_job_status` 为本实例只读核查的状态或“未部署/尚未登记/待核实”，写明用户授权 Agent 在执行 GPU 任务前直接停止当前实例、无需再次确认；非 KML 时删除该段，不带入 KML 路径或操作授权。
4. **必须在新 AGENTS 中显式规定：如果 GPU 所在服务器的实际可用存储空间与配额足够，每次模型训练与评测都必须持久化保留所有可取得的信息，包括完整 rollout 和 judge model 评分详情（若有）。** 按模板保留原始过程、失败/重试记录与恢复材料，启动前核对容量，空间不足或字段不可取得时记录证据、缺失范围与调整策略；大产物留在允许的运行时根，manifest 和小摘要入 Git。没有指定服务器时也保留这项条件性要求，不虚构远端容量。
5. 保留通用规范：开工与接手、可验收工作包的委派、版本与依赖追溯、匹配对照与冻结评测、预算与停止条件、失败和负结果账本、可恢复产物、项目级排障、具体事实汇报。不要继承 loyal-code 的契约修复、PRM、verl、模型、训练步数、历史预算或 kml-1005 配置；用户为新项目明确指定的要求另行写入。
6. 已有 `AGENTS.md` 时保留有用的项目规范并合并；只有用户要求替换时才重写，先保留可审阅 diff。未纳入 Git 的原文件先保留本机备份，备份不自动入库。
7. 建立或合并必要的 `.gitignore`，排除密钥、`.env`、私有 SSH 配置、环境、权重、大数据、checkpoint、大日志与运行时缓存。保留可追溯 manifest、小结果和文档；禁止忽略整个实验记录目录。

## 3. Git 初始化、私有 GitHub 仓库与首次推送

- 若尚无 Git，在工作区初始化 Git，初始分支通常为 `main`；已有 Git 保留历史、branch 和用户配置，不改写提交、不强制换分支。提交身份取现有有效 identity，不冒用他人。
- 使用本机 `gh` 核实身份与目标仓库。目标不存在时使用 `gh repo create <owner>/<project> --private`。目标已存在则核对 owner、权限、可见性与历史后复用；公共同名仓库不能擅自改私有，其他人或无关仓库不能覆盖。
- 同名 public 仓库与本次 private 要求冲突时，保留它及原 remote，先询问一个不同的私有仓库名，或采用用户已允许的替代名称；新私有目标确认后再设置本工作区 origin，原源码 remote 保留为 upstream。未解决命名冲突前只推进本机整理，不把 public 当作完成私有建库。
- 复现公开项目需要私有工作仓库时，clone 保留上游历史，并记录源 URL/commit。为新的私有仓库设置 `origin`；原来源保留为明确的 `upstream` 或其他无冲突名称。不要依靠 `gh repo fork` 推断新仓库会是私有。
- 审阅本次 diff 和待收录文件，用明确路径 `git add`。不盲目 `git add -A`；检查新增文件没有 secret 和大产物。没有改变就不制造空提交。
- 创建可审阅提交，通过本机认证的 Git 通道推送目标分支；默认 HTTPS 使用 `gh` 的凭据辅助或已有已验证通道，不改全局 Git/SSH 配置。已有仓库先 fetch，分叉保留证据并消解；只快进，不 force push、`reset --hard` 或 `clean -fd`。
- 确认 GitHub 为 private，记录 URL、branch 与首个提交。

## 4. 指定服务器时部署与调查资源

按 [远端部署流程](references/remote-bootstrap.md) 完成以下步骤，顺序保持依赖：

1. 核实 SSH 主机身份、用户、实际实例和允许根目录。KML 默认代码路径为 `/mmu_vlm_hdd/home/rhsu/playground/<project>`，运行时为同层 `<project>-data`；其他服务器按用户已有约定和可核实的常用路径，不能猜测。
2. 使用不覆盖远端修改的方式复制代码与 Git 历史；源代码和运行时分开，密钥通过独立私有通道处理。
3. 核查 launcher 与本次允许的 workers，逐节点只读查询 GPU、显存、挂载及连接；将能连接且允许使用的资源写进 AGENTS，失败项标 unknown。单节点检查或 hostfile 不证明总 GPU 健康与可用。
4. KML 资源核查与后续 GPU 安排必须应用可用的 **`kml-gpu-usage`** 技能，按其真实入口和本项目实例信息工作；把这条要求写进新 AGENTS。同时写入共享占卡入口 `/mmu_vlm_hdd/home/rhsu/idle-job-can-kill-anytime/idle-job`、本实例启用状态、实例隔离规则，以及执行 GPU 作业前的 `stop` / 前台 `run --` 操作与用户授权。工作区初始化阶段仅查询已有状态，不停止、部署或启用占卡；记录节点/卡的分配权限、核查时间和证据，不自动承诺所有 GPU 可调度。
5. 本机为此仓库生成专属读写 deploy key，用本机 `gh` 注册公钥，将私钥传至远端项目运行时私有目录，配置仓库级 SSH 通道。核验无 `gh` 登录的远端 fetch/push。

## 5. 最终提交、同步与交付

- 将新 AGENTS 的远端连接方式、绝对代码/运行时路径、实例/worker 清单和实测 GPU 资源补齐；公开仓库资料不得包含密钥、token、带凭据代理或 SSH 私有配置。
- 本机审阅最终 diff，选择唯一提交端，提交并再次推送。指定服务器时，优先由 launcher 提交刚补齐的真实资源/部署文档并用 deploy key 推送，再由本机 fetch、fast-forward 同步，这同时验收远端写权限。不能同时在两端编辑同一文件；若已由本机提交，用现有真实待提交改动核验远端写权限，没有改动就明确写权限仍未实证，不造测试提交。
- 同步前分别检查 dirty tree、branch 与远端历史，只做 fast-forward。共享 checkout 的 Git 写操作由 launcher 执行，避免本机和服务器同时写同一分支。
- 核对本机 HEAD、GitHub 目标 `refs/heads/<branch>`、服务器 HEAD 一致，并分别检查两端 working tree。未指定远端时仅验收本机与 GitHub，不伪造第三端状态。
- 无法完成某端时保留已完成步骤、提交/配置/错误与恢复动作，不宣布三端同步。网络或基础设施重试最多 2 次，恢复沿用已创建仓库和专属 key，先检查上次是否成功，不能重复创建。连接、仓库冲突或主机身份缺失只阻塞相关步骤，不用危险覆盖“修复”。

最终交付：本机路径、AGENTS 链接、私有 GitHub URL、branch/commit、可选服务器连接和路径、逐节点实测资源及限制、deploy key 的读写核验结果、两端工作树状态、未完成项。创建工作区完成后结束本流程；论文复现计划、训练和评测由用户另行指定。
