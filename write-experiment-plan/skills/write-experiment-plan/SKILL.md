# 写实验计划

把实验想法落实为另一位 Agent 可以接手实施的计划。默认用中文，保留必要的英文标识。给出有依据的主方案和明确取舍，不止列候选清单。计划深度与实验规模匹配；不适用的训练、分布式或统计环节说明原因即可。

## 先确定实验要回答什么

- 从用户描述、项目说明和已有代码中提取：方法改动、预期收益、待检验假设、对照、主要指标、资源和时间限制。保留用户明确选定的数据、模型与实验范围。
- 优先查看项目的 AGENTS.md、已有计划、配置、数据清单、训练/推理/评测入口和已有结果，确认哪些能力可复用。不要把不存在的脚本或旧结果写成已验证事实。
- 缺少信息时，先推进不受影响的调查。只有会改变核心方法、选型或可行性的缺口需要提问；其余给出明确标注的默认假设。无法访问资源时交付条件化方案，列出具体待核实项，不假装已经敲定。
- 写清“什么结果支持假设，什么结果推翻假设”。方法收益、机制诊断与工程可运行性分别判定，不能用显存利用率、注意力变化或跑通流程代替效果证据。

## 数据集、模型与证据

必要时联网：例如选型依赖近期发布、数据版本和可用性不明、缺少下载入口、模型支持范围不清楚。涉及“当前、最近、最新”等判断，先核对会话日期，再以该时间查询；不要用旧记忆断言现状。

优先查官方论文、代码仓库、数据/模型卡和正式托管页。打开并核实来源，区分项目主页、下载入口与具体版本。访问不了的链接标为未核实；不编造直链、提交号、容量或显存数值。

**数据选型应敲定：**

- 数据名称、版本、任务适配理由，以及训练、验证、开发测试和最终测试的用途；只做推理的实验说明不需要训练集。
- 规模、模态、标注字段、样本单位、划分规则、预处理、过滤和重复样本处理。按任务识别同源视频、主体或近重复样本泄漏；最终测试集不参与调参或筛选方法。
- 官方下载地址或仓库 ID、具体子集/config/split、访问或许可证条件、预计下载与展开体积、存储位置。无法核实的容量标为估算并交代依据。
- 如果采用自建或重划分数据，给出来源、生成规则、固定种子、样本清单保存方式和质量核验方法。不要只写“自行收集”。

**模型选型应敲定：**

- 精确模型/权重 ID、版本或 revision、下载地址、Base/Instruct 等变体、参数规模、输入限制和适配理由。区分架构、预训练权重、任务微调权重与自行训练部分。
- 明确冻结/训练的模块、全参或参数高效微调方案、精度和量化策略、推理后端与关键依赖兼容性；相关配置尚未实测时明确注明。
- 优先确定一个主方案。只有访问、资源或兼容性存在实际风险时给备选，并写清切换条件和对比较公平性的影响。

将关键选型集中为表格，附直接来源链接、核实日期和状态。下载命令只有在仓库/版本/工具用法已核实后才写；区分已执行命令与计划命令。不要把下载整个仓库作为默认方案，尽量限定所需文件和子集。

## GPU 资源与并行安排

目标是在资源许可范围内尽量提高有效吞吐。**已有任务占用不等于 GPU 不可用；只要实时可用显存足以容纳新任务及必要余量，就可以安排插入任务，不要求整卡或整节点空闲。**

- 在可访问且已授权的环境中读取实时资源快照，记录时间、机器、GPU UUID/编号、型号、总/空闲显存、利用率及相关 CPU、RAM、磁盘、互联限制。不要从旧快照认定可用资源，也不要终止或修改其他任务。
- 对训练、生成、评测和预处理分别估计资源。区分估算峰值和实测峰值，覆盖模型加载、优化器状态、激活、长输入/KV cache、评测切换等可能峰值。
- 规划小规模 smoke/profile，在代表性高负载配置上测显存峰值、吞吐和耗时；规划阶段尚未获准运行时，把它列为执行阶段的首个资源校准步骤。
- 同卡插任务的准入条件是：新增任务的预计峰值加必要余量不超过实时空闲显存。余量根据峰值测量覆盖度、分配器开销和其他任务波动设定，给出依据；没有数据时标为保守初估，待 profile 更新。
- 尽量并行独立 seed、消融、数据分片和评测；明确同卡多进程、跨卡数据并行、模型切分各自用途。增加进程后比较整体吞吐，若计算、I/O、CPU 或通信竞争使吞吐下降，则调整并发；不要只追求进程数量。
- 给出具体任务波次表：任务/依赖、GPU 分配或选择规则、单任务峰值、每卡并发、预计时长/卡时、输出和优先级。动态资源用调度规则加示例快照，不承诺固定可用卡数。
- 每次启动前重查容量；完成后释放资源并补入就绪任务。计划中写明 OOM 的并发/批量回退、checkpoint 恢复、有限重试与停止条件，避免无限重启。若用户指定时间或费用上限，调度需服从该上限。

## 代码管线与实现计划

结合仓库现状给出实际文件或拟新增文件的位置，并明确哪些已存在、哪些待实现。按依赖拆分工作，至少覆盖相关的以下环节：

1. 数据获取与校验 → 样本索引、固定 split、预处理/缓存。
2. 模型加载与基线复现 → 方法模块接入 → 训练或推理。
3. 原始预测落盘 → 指标计算 → 聚合比较和失败样本分析。

为每个模块说明输入/输出契约、关键配置、实现工作量或依赖、验收方式。配置覆盖数据/模型版本、seed、batch/梯度累积、学习率/训练预算或解码预算等实际相关参数；不能把关键取值全部留成“之后再定”。

设计统一实验 ID 和产物目录，保留配置快照、代码版本、样本 ID、日志、checkpoint、原始预测和汇总指标。说明断点续跑与去重/完成状态识别，避免失败恢复时重复生成或覆盖不同实验。

给出可执行入口和代表命令。未实现的入口标为“拟实现”，说明实现后的调用约定，不宣称现在可直接运行。验收应覆盖样本对齐、标签/指标正确性及端到端产物完整性；避免只检查进程退出码。

## 实验步骤与结果分析

采用与任务相称的分阶段方案，每一阶段写清入口条件、运行内容、产物以及继续/停止条件：

- **连通和正确性验证：** 少量样本跑通数据—模型—预测—评测；检查输入、目标、指标和资源峰值。
- **基线与开发实验：** 确认基线可复现，在开发集上筛选配置；先运行能快速否证核心假设的实验。
- **主实验与必要消融：** 实验矩阵逐行给出方法、对照、变量、固定项、预算、seed/重复和回答的问题。比较时匹配数据、backbone、训练和推理预算；额外预算是方法组成时单独报告质量—成本比较。
- **冻结配置后的最终评测：** 使用保留测试集及适当泛化测试，避免测试结果反复驱动调参。

预先指定主指标、方向和有意义的收益标准；再选成本指标、分组指标与诊断指标。根据样本和随机性来源选择多 seed、置信区间或配对比较，不机械要求所有实验使用同一种显著性检验。说明缺失、超时、格式错误和失败样本如何计入指标。

规划最终结果表、必要图、典型成功/失败样本和误差归因。分别解释“有效”“无明显收益”“退化”的后续决策；不预写正向结论，不把计划中的实验写成已取得结果。

## 交付

交付一份独立、可接手的实验计划。按项目约定保存；没有约定时使用 `docs/experiments/<实验短名>-plan.md`，只有聊天场景时可直接在回复中给出。正文应能定位到：

- 目标、假设与核心决策；
- 数据/模型选型及经过核实的下载来源；
- GPU 容量依据、并行安排与资源校准步骤；
- 代码模块、配置、实施依赖与运行入口；
- 实验矩阵、阶段步骤、分析规则和停止条件；
- 未决事项及其影响、假设/估算与实测事实的区分。

复杂计划附一段可交给实施 Agent 的提示词，引用计划位置、实施顺序、验收和执行范围。只有用户要求时才创建新任务。写计划本身不自动授权大规模下载、实现代码或启动长时实验；如果用户已明确同时授权这些工作，则在其范围内继续，不重复索要许可。

交付前检查：是否存在未作选择的关键候选、无法定位的下载来源、无容量依据的并发数、缺少对照的实验、测试集泄漏，以及把估算写成事实的表述。可解决的先解决，剩余项说明如何验证及其阻塞范围。
